# 开发与交付工作流

## 修改前：确认 Git 分支

- 修改任何代码或配置前，必须检查当前分支，并结合需求背景和提交历史判断任务应归属的目标分支；用户提出修改需求，不等于授权在当前分支修改。
- 当前分支与任务不匹配时，必须先说明情况并确认处理方案（切换分支、新建修复分支、使用 worktree 或后续 cherry-pick），不得直接修改。
- 切换分支或调整工作区前，必须保护现有未提交改动，禁止覆盖、丢弃或混入无关改动。
- 禁止将线上修复、其他功能或其他任务的改动混入当前开发分支。
- 提交前必须再次检查分支和变更清单，确认所有改动均属于目标分支和本次需求。
- 同时修改多个仓库时（如在后端目录下修改 `../xxx-crm`、`../xxx-mini`），每个仓库必须分别检查分支、核对变更清单、分别提交。
- Commit 信息必须简洁：使用一行标题说明改了什么，仅在必要时补充少量要点；禁止写入背景、过程或总结。
- 禁止在 commit message 中添加任何 AI 工具署名或生成标记，包括但不限于 `Co-Authored-By: Claude ...`、`Generated with Claude Code`。

## 开发阶段：自检与修复

- 自检属于开发阶段，由开发方在完成实现后执行；自检发现的问题可以直接修复。
- 自检必须对照原始需求和项目检查规范逐项进行，不能只检查本轮修改点，也不能只说明“已检查”。
- 项目存在 `REVIEW_PROMPT.md` 时，自检必须对照其逐项执行。
- 自检通过仅表示可以提交验收，不等于验收通过；开发方不得据此自行宣布验收通过。

## 交付阶段：独立验收

- 验收必须由独立于开发方的验收方执行，并与开发自检分离。
- 项目存在 `REVIEW.md` 时，独立验收按其执行。
- 验收方对被验收内容只读不写：只允许检查并输出验收报告或问题清单，禁止修改代码、配置、业务数据及其他被验收内容，禁止直接修复问题。
- 验收必须以原始需求为基准，覆盖相关业务流程、代码和模块，不得局限于本轮修复点；修复可以针对单点，验收必须覆盖完整需求及影响范围。
- 必须主动检查功能完整性、业务逻辑、边界条件、异常处理、权限、数据一致性以及模块间影响。
- 发现一类问题后必须举一反三，排查所有相关页面、接口和模块中是否存在同类问题。
- 前后端功能必须执行端到端完整链路验证；仅编译通过、单元检查通过或单个接口正常，均不算验收完成。
- 验收报告必须明确区分“本次重点验证范围”和“回归范围”。
- 问题清单必须写明问题位置、复现方式、预期行为和实际行为，并交回开发方修复。
- 修复完成后必须重新提交独立验收；验收方仍只审不改，开发方不得自行宣布验收通过。

## Skills 使用边界

- 本文件规则与项目现有代码风格优先于任何 Skill 的通用建议；冲突时按本文件执行，不得为套用 Skill 重构现有架构。
- systematic-debugging 仅用于开发方排查 Bug；验收方只可读代码、读日志、复现，禁止加诊断代码或修复。无法写自动化测试时，以“复现步骤 + 日志/截图证据”代替失败测试。
- verification-before-completion 用于自检阶段的完成声明，证据写入自检结果；验证命令必须只读（禁止 `--fix`/`--write`，禁止为通过验证修改 go.mod 的 go/toolchain 版本），真机、支付、授权、第三方回调等终端无法验证的必须标注“未验证，需人工”；不能替代独立验收。
- Codex review-agent、Claude `/code-review` 仅作 diff 缺陷扫描，不能替代独立验收。
- golang-pro 仅作 Go 写法参考；golangci-lint、覆盖率要求、接口先行、导出注释、functional options 等不作为强制要求，除非任务明确要求。

# GORM
- 禁止在 for 循环中执行sql
- MySQL8 中优先使用递归
- GORM 事务优先使用 db.Transaction()，自动处理 commit/rollback
- 仅在需要跨层传递或复杂流程控制时才使用手动 tx.Begin()
- 如必须使用手动事务，必须保证所有分支都有 Commit 或 Rollback
- 禁止事务中包含慢接口、远程请求、文件上传等耗时操作
- 事务内只放必须保证一致性的数据库操作
- 错误事务处理可能导致锁长期不释放，引发大量锁等待
- 高并发场景必须控制事务范围，避免长事务扩大锁影响

# 数据库
- 严格使用真实字段名
- 不允许猜字段
- 不允许自动生成不存在字段
- SQL 必须确认：
    - LEFT JOIN 是否导致重复数据
    - OR 条件是否导致索引失效
    - 实时写入是否导致结果不一致
- 涉及并发数据时，优先使用行锁，避免表锁
- 必须确认 where 条件命中索引，否则可能退化为大量锁记录
- 锁范围必须最小化
- 长事务必须确认是否阻塞其它业务
- 必须确认是否可能产生死锁  

# 幂等
- 支付/退款/回调接口必须考虑幂等
- 高并发场景必须防止重复提交
- “先查询不存在，再新增”不具备并发安全性；普通事务、前端防抖和按钮禁用不能替代服务端并发控制
- 创建订单、报名、领取等不可重复业务，必须按真实业务唯一维度建立数据库唯一约束兜底
- 存在有效、删除、取消等状态时，唯一约束只能限制有效数据，不得误伤历史数据
- 唯一约束冲突必须转换为明确的业务提示，并确认同一事务内的库存、额度等资源变更已回滚
- 库存、名额、次数等资源必须使用带剩余量条件的原子更新，并检查影响行数，禁止事务外查询后再无条件更新
- 必须全局检查所有写入入口是否遵守相同的防重、错误处理和事务规则

# 状态机
- 状态流转必须校验当前状态
- 禁止跨状态直接更新

# 排查
- 代码逻辑正确、前端传参正确，但线上行为与预期不符时，优先确认后端是否已部署最新代码
