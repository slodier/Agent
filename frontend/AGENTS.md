# Vue3

## 写完代码后
- 必须对照 `REVIEW_PROMPT.md` 逐项自查，不能只说"已检查"

## 上线前确认

- 涉及时间/配置的需求，必须在需求方明确确认后再开始写代码，不允许自己估一个值
- 活动结束时间、按钮显示时间等写死在数据库/配置里的值，开发前必须有明确来源
- 有口头改动（如群里说"改成4号结束"）必须同步确认后再动代码，不允许凭记忆实现
- 有任何未确认的配置/时间/规则时，不允许上线

## 日期时间

- 涉及"日期/天数/签到/排行/今日/昨日"等业务时，必须先确认时区：
  * UTC
  * 用户本地时区
  * Asia/Shanghai（北京时间）
  * 或服务端固定时区
- 时区未明确前，不允许擅自实现日期逻辑
- 禁止使用 `new Date('YYYY-MM-DD')` 解析业务日期
  * `YYYY-MM-DD` 会按 UTC 0 点解析，东八区会变成当天 08:00
- 按北京时间/业务日期计算时，必须固定 Asia/Shanghai
- 起始日必须用以下方式之一：
  * 服务端返回时间戳
  * `new Date(year, month - 1, day)`
  * 服务端返回 YYYY-MM-DD 后，拆分成年月日再构造 Date
- 禁止把"服务端时间戳"和"前端本地时区日期"混算
- 时间戳必须确认是秒还是毫秒
- 计算天数前，必须确认基准是 UTC 日期、用户本地日期还是北京时间业务日期
- 活动时间限制必须在服务端校验，前端禁用按钮/路由拦截只是体验层，不是安全层
- 页面必须在 onLoad/onShow 时主动拉取并校验活动状态，不能依赖上一页传参——用户可以直接访问路由绕过入口

## 分类 / 类型扩展

- 新增分类或修改某一分类逻辑时，必须通过分类 ID/类型字段做条件判断，禁止直接修改公共逻辑
- 禁止把某一分类的特殊规则（上传限制、表单提示、审核流程）写进公共组件/公共函数
- 修改公共组件/公共函数前，必须列出所有调用方，确认其他分类行为不受影响
- 仅拍照的分类，`chooseImage` 的 `sourceType` 只传 `['camera']`，不允许保留相册入口
- 新分类的特殊提示文案必须通过条件判断输出，不允许覆盖其他分类的文案

## 代码风格

- 必须使用 setup 语法，禁止 Options API
- 使用箭头函数
- composable 按功能拆分，超过一个文件复用的逻辑必须抽 composable
- props/emits 必须定义类型
- 禁止滥用 watch，使用前先确认 computed 是否更适合

## 请求

- 登录失效统一处理：`return new Promise(() => {})`，不允许 `Promise.reject('')`
- 请求必须加锁防重复触发，包括：表单提交、列表、按钮、初始化请求
- 列表页切换 tab/筛选条件时，必须取消上一个请求（AbortController）
- 删除操作必须二次确认

## 交互 / UX

- 需要 loading 状态时，必须先确认展示方式：组件覆盖、按钮 disabled、按钮文案变更、骨架屏等；需求未明确前禁止擅自决定
- 任何 UI/UX 细节若需求未明确，必须先询问再实现，包括但不限于：loading 表现、错误提示样式、空状态展示、动画效果、成功反馈方式、按钮禁用态

## 表单

- 提交前必须 trim 字符串，防止空格导致校验通过但数据异常
- 金额、手机号、身份证等必须前端格式校验，不能只依赖后端

## 样式

- 禁止 inline style，统一使用 class
- uniapp 单位使用 rpx，其它场景使用 px
- 禁止滥用 `!important`
- 禁止使用 tailwind class，除非项目已明确接入 tailwind.css（HBuilder/uniapp 环境不支持）
- 从蓝湖/墨刀复制 html/css 后，必须去掉无用结构和样式，禁止保留无意义 div 嵌套
- 暗色/亮色状态必须确认

## 组件通信

- 禁止子组件直接修改 props，必须通过 emit
- 禁止多层 props drilling，跨层级通信使用 provide/inject 或 pinia

## 权限与路由

- 路由必须懒加载，禁止全量 import
- 动态路由必须在登录后重新初始化

## 性能

- 禁止在 template 中写复杂表达式，必须抽成 computed

## 排行 / 排名

- 排名必须基于全量数据计算，禁止基于当前页数据计算
- 分页参数 offset/page 必须正确传给接口，第二页第一条的排名必须接续第一页
- 前三名的特殊样式（金银铜牌）只能判断全局排名字段，禁止用当前页的数组索引判断

# UniApp / 小程序

## 平台能力

- web-view 跳小程序使用：`wx.miniProgram.navigateTo`
- 小程序内 H5 / web-view 链接必须使用 `https`
- 图片长按识别使用：`show-menu-by-longpress`
- web-view 中 H5 页面长按二维码，仅支持微信体系：
  * 小程序码、微信个人码、企业微信个人码
  * 普通群码、互通群码、公众号二维码
  * 其它二维码不保证支持，属于微信能力限制
- `chooseImage`/`chooseVideo` 返回会触发 onShow，注意副作用
- `uni.showToast` 可能被系统清掉，关键提示勿依赖
- 小程序分享路径参数必须 `encodeURIComponent`，落地页读取后必须解码并校验
- 二维码/小程序码 scene 参数长度有限，复杂参数必须换成短码后到服务端换取详情
- 跳转 tabBar 页面必须用 `switchTab`，普通页面使用 `navigateTo`，重定向使用 `redirectTo`
- 自定义 tabbar 跳转必须使用 `redirectTo`，禁止一直 `navigateTo`
- `navigateTo` 页面栈最多 10 层，超过后会报错；连续跳转流程必须确认是否需要 `redirectTo` 或 `reLaunch`
- 调用小程序 API 必须处理 fail/complete 分支，禁止只写 success 分支
- 小程序 API 回调和 Promise 封装不能混用到漏处理异常，必须统一返回结果和错误

## 授权 / 隐私

- 获取手机号、头像昵称、定位、相册、摄像头等能力前，必须确认微信最新授权方式和隐私协议配置
- 权限拒绝后必须提供可恢复路径，不能假设用户一定授权
- `getUserProfile`、头像昵称填写能力、手机号获取能力变更频繁，开发前必须确认当前基础库和微信官方规则
- 订阅消息必须由用户主动触发授权，禁止在页面初始化时静默请求
- 授权状态不能只读缓存，进入关键流程前必须重新确认当前权限状态
- 用户取消授权、接口返回空 code/空 encryptedData/空 phoneNumber 时必须有明确处理分支

## 开发注意

- 代码确认无误但多次修改不生效时，尝试关闭 HBuilder 后重新运行微信小程序
- 不允许频繁 onLoad 请求
- onLoad 只适合处理页面参数和首次必要初始化，返回页面刷新优先在 onShow 中做差异判断，必须避免 onLoad/onShow 重复请求
- onShow 中发请求必须加来源判断或节流锁，避免 chooseImage、支付、授权、从 H5 返回时重复触发
- 小程序启动参数、分享参数、扫码参数都必须兼容缺失、非法、重复进入的情况
- 扫码 scene、分享 query、普通路由 query 的解析必须统一，禁止多个页面各写一套不一致解析逻辑
- 页面跳转前必须确认参数是否超长，复杂对象禁止直接 JSON stringify 后拼到 URL
- 真机表现必须验证，不能只看开发者工具；涉及相机、相册、定位、蓝牙、支付、web-view、长按识别时必须真机测试
- 必须确认安卓/iOS 差异
- 必须确认微信/支付宝差异
- setData / 响应式数据更新禁止一次性塞入大对象或长列表，避免页面卡顿和通信数据过大
- 本地缓存必须确认 key 命名、过期策略和清理策略，禁止把登录态、活动状态等长期当作可信来源
- 小程序胶囊、状态栏、安全区高度必须用系统信息计算，禁止写死顶部间距
- 自定义导航栏必须处理状态栏高度、安全区、胶囊位置和横竖屏变化
- 页面卸载时必须清理定时器、轮询、事件监听、音视频实例、地图/蓝牙等资源
- **JnChart 不显示**：不能把高度 class 直接加在 `<JnChart>` 组件上，scoped 内部样式 `height:100%` 优先级更高会覆盖外部 class，导致 canvas 高度为 0。必须用 `<view>` 包一层并在 view 上设定高度，JnChart 内部 canvas 通过 `height:100%` 继承。示例：`<view style="height:240px"><JnChart :option="opt"/></view>`

## 性能

- 长列表必须分页
- 图片必须懒加载
- 视频必须确认码率
- 大图、背景图、动效资源必须压缩，禁止把未压缩设计稿直接放入包内
- 列表图片必须控制尺寸和数量，禁止原图直出导致内存暴涨
- 列表分页必须处理 loading、finished、error、empty 状态，禁止只判断数组长度
- 下拉刷新和上拉加载必须共用同一套分页状态，避免刷新后 page/pageSize/finished 状态错乱

## 支付 / 交易

- 支付结果必须以服务端订单查询为准，前端回调只作为触发刷新，禁止仅凭 `requestPayment` 成功回调改业务状态
- 支付后从微信收银台返回会触发 onShow，必须避免重复创建订单或重复支付
- 订单、抽奖、报名等关键操作必须服务端防重，前端按钮锁只能做体验层保护
- 创建订单、拉起支付、查询订单必须分成明确步骤，禁止在 onShow 中无条件重新创建订单
- 支付取消、支付失败、查询订单失败必须区分处理，禁止统一当作支付失败或支付成功

## 动画框架

- 官网/落地页/营销页面向外部用户的前台系统, 考虑引入 GSAP（ScrollTrigger、Timeline）
- 管理后台、小程序禁止引入 GSAP，用 Vue Transition 或 CSS 动画替代
- Animate.css 可按需搭配用于补充具体动画效果
